## Problem Statement

CallBridge already lets ChatGPT prepare, revise, inspect, and monitor a controlled inquiry through WebMCP. The page currently renders a fixed call brief, Activity, and result. It cannot yet represent the task-specific surfaces that appear during a real concierge workflow: a text conversation with a hotel, a question that needs the user's answer, an authorization handoff, or approved visual evidence.

The selected direction is a typed artifact layer. WebMCP creates and updates structured task artifacts. Convex owns their durable state and revisions. React maps each approved artifact type to a fixed component. The model never supplies arbitrary HTML, JavaScript, or CSS.

## What Makes This Cool

The page visibly reshapes itself around the work:

1. ChatGPT creates an inquiry through the existing WebMCP contract.
2. A provider requires account access, so an `auth_required` card appears.
3. The user completes sign-in in a protected browser flow; no password enters an artifact.
4. A `conversation` artifact appears when a real text channel exists.
5. New provider messages, evidence, and questions update the page in place.
6. The existing result projector closes the task without adding a second result system.

The wow moment is observable: one WebMCP call changes durable task state and a purpose-built artifact appears on the same signed-in page.

## Confirmed Decisions

- Use a typed Artifact Layer, not state-only conditional rendering and not a full multi-channel inbox.
- ChatGPT remains the main conversational layer. The webpage shows task-specific artifacts rather than a second general chatbot.
- WebMCP creates or updates structured records. React renders only approved component types.
- External transport is separate. SMS, email, WhatsApp, telephony, or a provider API delivers messages; WebMCP does not.
- Consequential actions such as sending, confirming, paying, accepting terms, or changing an account remain separate user-confirmed operations.
- Third-party authentication is represented by an `auth_required` artifact, but credentials and session tokens never enter artifact storage.

## Premises

1. WebMCP is the page-to-agent action contract, not a renderer, credential vault, or channel transport.
2. The current Convex ownership, revision, confirmation, Activity, and result boundaries remain authoritative.
3. Third-party claims must come from a trusted channel adapter or accepted provider evidence. The model cannot fabricate a hotel message by writing a `conversation` artifact.
4. A screenshot is evidence produced by an approved capture or upload flow. WebMCP may attach its reference and metadata but does not silently capture arbitrary screens.
5. The hackathon slice demonstrates dynamic artifacts on one controlled task. General multi-channel inbox behavior remains post-hackathon.

## Scope

### In scope

- A discriminated `TaskArtifact` contract with strict payload schemas.
- Four initial artifact types: `conversation`, `auth_required`, `user_question`, and `evidence`.
- Convex-backed ownership, ordering, revisions, visibility, and audit events.
- Narrow WebMCP tools for creating, updating, and reading artifacts.
- A React artifact registry with one fixed renderer per type.
- Same-page updates after a tool call and restoration after refresh.
- A controlled demo that shows at least three artifact types.
- Tests proving authorization, revision conflicts, source integrity, and the absence of model-invocable consequential actions.

### Out of scope

- A general-purpose inbox with arbitrary threads and recipients.
- Shared artifact membership; the hackathon model remains owner-only.
- Direct password capture, password storage, or session-token storage in Convex.
- Universal login automation for third-party websites.
- A generic HTML or component-generation tool.
- Real WhatsApp, Viber, Telegram, Booking, or Airbnb adapters unless an already-authorized official integration is available.
- Fabricated external messages or unlabeled simulation in production Activity.

## Artifact Contract

All artifacts share a server-owned envelope:

```ts
type TaskArtifact<T extends ArtifactPayload = ArtifactPayload> = {
  schemaVersion: 1;
  artifactId: string;
  taskId: string;
  createdSequence: number;
  lastEventSequence: number;
  revision: number;
  type: T["type"];
  status: "active" | "resolved" | "superseded" | "failed";
  visibility: "owner";
  source: "chatgpt" | "callbridge_server" | "channel_adapter" | "user";
  payload: T;
  createdAt: string;
  updatedAt: string;
};
```

The server assigns `artifactId`, both sequence values, timestamps, ownership, and accepted source. `createdSequence` orders artifact creation; `lastEventSequence` advances on every accepted change and is the read cursor. A WebMCP caller may propose content permitted by the type schema, but it cannot self-assert `channel_adapter` or provider provenance.

### `conversation`

Represents a real external text exchange or a bounded CallBridge conversation projection.

```ts
type ConversationArtifact = {
  type: "conversation";
  channel: "sms" | "email" | "whatsapp" | "web_chat" | "call_facts";
  title: string;
  participants: Array<{ id: string; displayName: string; role: "user" | "agent" | "provider" }>;
  latestMessages: Array<ConversationMessageProjection>;
  hasEarlierMessages: boolean;
};
```

Conversation messages live as append-only event rows with their own idempotency keys. `latestMessages` is a bounded materialized projection, avoiding whole-array conflicts and document growth. Provider-authored messages are appended only by a trusted adapter or evidence projector. WebMCP may create the container or append an agent-authored draft, but it cannot mark a message as provider-authored, submitted, delivered, or observed.

For phone calls, the artifact uses `call_facts` and contains bounded public facts, not a raw transcript or hidden reasoning.

### `auth_required`

Represents an external sign-in handoff without storing credentials.

```ts
type AuthRequiredArtifact = {
  type: "auth_required";
  providerId: string;
  providerName: string;
  reason: string;
  state: "required" | "waiting_for_user" | "authorized" | "expired" | "failed";
  continuation: "open_secure_browser" | "oauth_redirect" | "return_to_task";
};
```

`providerId` must resolve through a server-owned allowlist to the authorization destination; the model never supplies an origin or redirect URL. The artifact may open a protected browser or OAuth flow. Passwords, one-time codes, cookies, refresh tokens, and access tokens are prohibited payload fields. Free-text fields pass length limits plus secret-pattern redaction/rejection. The authorization callback returns only an opaque status bound to the task and provider. The authorization result is accepted only from the browser/auth integration, never from a model-written update.

### `user_question`

Shows a short prompt only when the workflow cannot continue without input.

```ts
type UserQuestionArtifact = {
  type: "user_question";
  prompt: string;
  responseMode: "text" | "single_choice" | "multi_choice";
  options?: Array<{ id: string; label: string }>;
  response?: { value: string | string[]; submittedAt: string };
};
```

### `evidence`

Displays an approved screenshot, document, or provider receipt.

```ts
type EvidenceArtifact = {
  type: "evidence";
  kind: "screenshot" | "document" | "receipt";
  assetRef: string;
  caption: string;
  capturedAt: string;
  provenance: "user_upload" | "browser_capture" | "provider_receipt";
  redactionState: "not_required" | "redacted" | "blocked";
};
```

`assetRef` points to server-authorized storage. The page never renders arbitrary external URLs supplied by the model.

`decision` is deferred because the demo's bounded choices fit `user_question`. The existing evidence-bound result projector remains authoritative rather than becoming a second artifact type.

## WebMCP Surface

Add three tools alongside the existing five:

| Tool | Purpose | Consequential? |
|---|---|---|
| `create_task_artifact` | Create a schema-valid non-consequential artifact for an owned task | No |
| `update_task_artifact` | Update an exact artifact revision within allowed state transitions | No |
| `read_task_artifacts` | Read changed public artifacts after an optional event cursor | Read-only |

Tool inputs stay narrow:

```ts
type CreateTaskArtifactInput = {
  schemaVersion: 1;
  taskId: string;
  expectedTaskRevision: number;
  idempotencyKey: string;
  artifact: CreateArtifactPayload;
};

type UpdateTaskArtifactInput = {
  schemaVersion: 1;
  taskId: string;
  artifactId: string;
  expectedArtifactRevision: number;
  idempotencyKey: string;
  patch: WebMCPAllowedArtifactPatch;
};
```

The server rejects unknown keys, arbitrary URLs, source escalation, terminal-state reopening, unsupported channel claims, and payloads that imply an external side effect.

`CreateArtifactPayload` and `WebMCPAllowedArtifactPatch` are writer-specific discriminated unions. They structurally omit user responses, authorization resolution, provider-authored messages and delivery states, evidence attachment, and result publication. Page mutations and trusted adapters use separate input unions, so forbidden fields are absent from the WebMCP schema as well as rejected at runtime.

### Writer capability matrix

| Mutation | WebMCP | Page mutation | Trusted callback/adapter |
|---|---:|---:|---:|
| Create an artifact container | Yes | No | Yes |
| Add or revise agent-authored draft text | Yes | No | No |
| Submit a user's question response | No | Yes | No |
| Resolve provider authorization | No | No | Yes |
| Append provider-authored message/status | No | No | Yes |
| Attach approved evidence | No | Yes, upload only | Yes |
| Publish final result or execute protected action | No | No | Existing protected path only |

The mutation layer enforces this matrix per field and state transition; the broad tool names do not imply broad patch authority.

No tool named `send_message`, `submit_form`, `confirm_call`, `pay`, `accept_terms`, or `store_credentials` is added in this slice.

## Runtime Flow

```text
ChatGPT Work or Codex
  -> WebMCP tool on the CallBridge page
  -> authenticated client adapter
  -> Convex mutation validates owner, task state, schema, revision, and policy
  -> taskArtifacts row plus monotonically sequenced artifact event
  -> live query or bounded polling returns current projection
  -> React ArtifactRegistry renders the matching fixed component
  -> agent inspects the page change
```

External inputs follow a different path:

```text
provider channel or browser integration
  -> trusted adapter / signed callback
  -> source validation and evidence binding
  -> artifact event or message append
  -> same Convex projection and React renderer
```

## Authentication Boundary

There are three distinct cases:

1. **CallBridge login:** existing WorkOS/AuthKit and Convex authentication remain unchanged.
2. **OAuth-capable provider:** use the provider's official OAuth or connector. The artifact records only state and display metadata.
3. **Website username/password:** show `auth_required`, open a protected browser handoff, and let the user enter credentials there. CallBridge does not collect or store them. Whether the browser persists a signed-in session is controlled by that browser/auth layer, not WebMCP.

If the third-party page itself supports WebMCP, its tools belong to that page and signed-in session. CallBridge's WebMCP tools do not inherit or impersonate another site's tools.

## React Rendering

Use a fixed registry:

```ts
const artifactRenderers = {
  conversation: ConversationArtifactView,
  auth_required: AuthRequiredArtifactView,
  user_question: UserQuestionArtifactView,
  evidence: EvidenceArtifactView,
} satisfies ArtifactRendererRegistry;
```

Unknown artifact types render an explicit unsupported-state card and never execute payload content.

The page remains a task workspace:

- artifacts are ordered by server creation sequence and refreshed by event sequence;
- unresolved user questions receive focus priority;
- resolved artifacts remain reviewable but visually quieter;
- one contextual input may appear inside `user_question` or a draft message;
- there is no permanent general composer competing with ChatGPT;
- inbox navigation, if shown, lists tasks rather than arbitrary conversations.

## Convex Storage

Introduce:

- `taskArtifacts`: current materialized artifact envelope and payload;
- `taskArtifactEvents`: append-only accepted changes for audit and restoration;
- `conversationMessages`: append-only conversation entries with per-entry idempotency and provenance;
- indexes by owner/task/creation sequence, task/event sequence, task/status, and conversation/message sequence;
- bounded retention inherited from the parent task unless a stricter evidence policy applies.

Large evidence bytes remain in approved object storage. Convex stores only references, hashes, MIME type, size, provenance, and redaction state.

## Safety and Trust Rules

- Every query and mutation validates authentication, task ownership, and current revision.
- Model-written content is untrusted and displayed as such where authorship matters.
- Provider authorship and delivery status are server-assigned.
- Evidence URLs are resolved from approved storage, not rendered directly from model input.
- Artifacts cannot create external effects.
- Page-only and trusted-writer fields cannot be patched by WebMCP.
- Secrets are excluded from schemas, logs, errors, Activity, artifacts, and WebMCP results.
- Free-text payloads are bounded and rejected or redacted when they resemble credentials or tokens.
- Provider redirects resolve from server configuration; callback destinations are never model-authored.
- Simulated channel content is labeled and cannot appear as observed production evidence.
- Raw call transcripts remain outside the public artifact projection.

## Alternatives Considered

### State-derived UI only

Rejected for this feature because it would be fast but would not visibly demonstrate WebMCP creating reusable task artifacts.

### Full multi-channel inbox

Deferred because channel adapters, delivery receipts, recipient permissions, retention, and reconciliation would overwhelm the hackathon slice.

## Hackathon Demo Slice

Use one controlled task and demonstrate:

1. `create_call_draft` creates the task.
2. `create_task_artifact` adds an `auth_required` card for a controlled provider fixture.
3. The user completes a safe controlled sign-in or explicitly labeled authorization fixture.
4. A trusted fixture or real authorized adapter appends one provider message to a `conversation` artifact.
5. WebMCP creates a `user_question` artifact.
6. The user responds in the page.
7. An approved screenshot appears as `evidence`.
8. The workflow ends with the existing evidence-bound result projector.

Do not claim universal third-party login support. The demo proves the artifact architecture and one controlled handoff.

## Success Criteria

- The latest supported ChatGPT browser discovers all artifact tools.
- A tool-created artifact becomes visible on the same page without reload.
- Refresh restores identical artifact ordering and resolved state.
- Duplicate idempotency keys do not create duplicate artifacts.
- Stale task or artifact revisions return a stable conflict error.
- A model cannot mark a message as provider-authored or delivered.
- A WebMCP writer cannot submit the user's response or resolve authorization.
- A model cannot store credentials, tokens, arbitrary URLs, HTML, scripts, or CSS.
- A protected action is absent from the artifact WebMCP surface.
- An authorization callback, not a model update, resolves `auth_required`.
- Provider destinations resolve from an allowlisted `providerId`; raw redirect origins are rejected.
- Updates remain visible after a reader advances its event cursor.
- Concurrent adapter appends and agent drafts remain ordered without replacing a whole message array.
- Evidence rendering rejects unapproved or unredacted assets.
- Existing call-draft, confirmation, dispatch, Activity, and result behavior remains unchanged.
- The public demo clearly labels any fixture or simulation.

## Test Plan

### Contract tests

- accept each valid artifact payload;
- reject unknown keys and cross-type patches;
- reject credential-like and arbitrary executable payload fields;
- reject provider impersonation, user-response impersonation, and model-authored redirect destinations;
- preserve stable serialization and error codes.

### Convex tests

- owner-only authorization and cross-owner denial;
- exact task and artifact revision enforcement;
- idempotent creation;
- ordered creation and event-sequence projection;
- concurrent message append and bounded projection;
- retry/idempotency after uncertain update success;
- source and provenance assignment;
- terminal and superseded state invariants;
- retention and evidence reference cleanup.

### WebMCP tests

- register exactly the approved artifact tools;
- mark only `read_task_artifacts` read-only;
- preserve abort signals;
- map internal errors to non-leaking public errors;
- exclude consequential tools and credential fields.

### UI tests

- renderer selection for every artifact type;
- unknown type fallback;
- empty, loading, error, resolved, and superseded states;
- accessible focus when a question becomes active;
- responsive conversation and evidence layouts;
- refresh and multi-tab conflict behavior.

### Browser acceptance

- invoke each artifact tool in the supported built-in browser;
- verify same-page visual change;
- complete the controlled auth handoff;
- confirm a provider message can only arrive through the trusted path;
- confirm owner-only denial and callback destination validation;
- inspect recently used site tools and visible result.

## Distribution

The existing public HTTPS web deployment remains the delivery surface. The artifact tools are available only when the current page and ChatGPT browser support WebMCP. The normal human UI remains functional without WebMCP, but agent-created artifacts require a supported environment.
